## Context

A clinic administration system built for ITC 6000, Database Management Systems, at
Northeastern. Ten tables in third normal form, a REST API over them, and a React front
end that runs the whole clinic workflow: registry, scheduling, encounters, ICD-10
diagnoses, invoices and payments.

The data is generated. `server/seed.js` builds 5,000 patients with portal accounts for
about 60% of them, then 12,000 appointments and the encounter, invoice and payment
records that hang off those — using Faker, not a real patient record anywhere. It's
there to make query performance and the constraints mean something at a size a
hand-typed fixture can't reach.

## The problem

[INFERRED] A schema is easy to draw and hard to trust. The interesting question isn't

database holds — and with billing split across invoices and payments, and diagnoses
joined through a bridge table, there are several places for those to drift apart.

## Constraints

**Foreign keys are enforced, not decorative.** `PRAGMA foreign_keys = ON` at the top of
the schema, and every relationship is declared. SQLite doesn't do this by default, so
without that line the constraints are documentation.

**The interesting cardinalities are one-to-one, and they're enforced by UNIQUE, not by
convention.** A portal account belongs to exactly one patient; an encounter belongs to
exactly one appointment; an invoice belongs to exactly one encounter. Each is a
`NOT NULL UNIQUE` foreign key, so the database refuses a second one rather than
trusting the API not to write it.

**Status fields are constrained to their real domains.** Appointments are checked
against `Scheduled / Checked In / Completed / Cancelled / No-Show`, encounters against
`Open / Signed`, invoices against `Open / Partial / Paid`, payments against
`Card / Cash / Check / Insurance`. Money is checked too: totals and amounts paid must
be non-negative, and a payment must be strictly positive.

**A diagnosis can only be attached to an encounter once.** `UNIQUE (FK_ENCOUNTER_ID,
FK_DIAGNOSIS_ID)` on the bridge table, with `IS_PRIMARY` as a flag rather than a
separate table.

**The browser gets its own database.** The SQL viewer runs SQLite in WebAssembly via
sql.js against an 8-patient sample committed to `public/`, so the viewer works on a
static deploy with no server. The full 5,000-patient database is built by the seed
script server-side. Why there are two is under Decisions.

## What I built

<ErdDiagram />

Ten tables, drawn above from the schema rather than from a screenshot of it.

The API is Express over better-sqlite3 — 41 routes. Full CRUD on patients, providers,
locations, appointments, encounters and invoices; nested reads for a patient's
appointments, encounters and invoices; payment recording against an invoice;
diagnosis attach and detach on an encounter; and a global search across patients and
providers.

Four of those routes exist only to serve the dashboard, and they're the ones doing
real SQL rather than row lookups: KPI totals, revenue by provider, appointment status
distribution, and a twelve-month revenue trend. Two more (`/api/meta/schema` and
`/api/meta/queries`) exist to feed the schema view and the SQL viewer — the
introspection that makes the traceability claim checkable rather than asserted.

The front end is React on Vite, with Recharts for the charts, shadcn and Radix for the
components, and a `Cmd+K` command palette over the search endpoint. Provider
productivity is computed as signed visits, gross billed, collected, and collection
rate. Billing shows an invoice ledger filterable by status with a payment workflow
behind it. CSV export takes a column selection, a scope of current page or all
matching rows, and the active filters.

It's deployed on Render via `render.yaml`.

## Decisions

### 3NF over a star schema

Reporting was half the point of this system, which is the usual argument for a star
schema — denormalise, accept the redundancy, make the reads fast.

I went with 3NF anyway, because the other half of the point was that the reports had
to agree with each other. In a star schema the same fact can be stored in more than one
place, and once that's true, two reports can both be correct and still disagree. That's
exactly the failure this system existed to eliminate.

3NF means every fact lives in one table and every relationship is a foreign key. Nine
foreign keys, `PRAGMA foreign_keys = ON`, all three one-to-one relations enforced by
`UNIQUE` rather than convention, status fields constrained by `CHECK`, and money
constrained to be non-negative on invoices and strictly positive on payments. A report
that disagrees with another report is a query bug, not a data bug, and query bugs are
findable.

That's also why there's a live SQL viewer tracing each dashboard metric back to its
source table. If someone questions a number, the answer is the query, not an
explanation.

The tradeoff is joins. Provider productivity crosses appointment, encounter, and
provider; billing crosses encounter, invoice, and payment. At 5,000 patients and
12,000 appointments that's not a problem. At a real clinic's volume I'd expect to add a
reporting layer on top rather than denormalise underneath.

### The sql.js split

The demo runs SQL in the browser through sql.js, and the database file it loads has
eight patients in it. The real one has five thousand.

sql.js loads the entire database into browser memory as a single file, so committing
the full seed would mean a multi-megabyte binary in the repository that every visitor
downloads before the page is usable — to run queries whose answers a dashboard already
displays. The eight-patient file proves the viewer works and the queries are real. The
5,000-row database is built server-side by the seed script, which is where the
query-performance claims come from.

So there are two databases doing two jobs: one to demonstrate that metrics trace back
to source tables, one to validate that the schema holds up at scale.
